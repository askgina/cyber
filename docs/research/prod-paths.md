# Production paths and gates

Research for [#35](https://github.com/askgina/cyber/issues/35). Decision input for [#37](https://github.com/askgina/cyber/issues/37).

## Answer

Cyber has two independent publishers: GitHub Actions deploys the Worker, static assets, and Builder image. Cloudflare runs the deployed Builder to publish new data, pages, and search documents from the current `main` tarball. The live `main` ruleset requires the PR `check` job, but that job does not run the full pipeline or check the production artifacts. A pipeline-only merge triggers **no GitHub Actions workflow on the `main` push**. Its PR runs CI, and the Cloudflare schedule can publish the change without Deploy or Post-deploy verification. (`.github/workflows/ci.yml:3–31`, `.github/workflows/deploy.yml:3–14,27–38`, `wrangler.jsonc:32–35`, `container/server.py:14–20,73–95`.)

## What the checks actually cover

- **PR CI (`check`, required).** [Ruleset 28174271](https://github.com/askgina/cyber/rules/28174271) is active on the default branch (`main`). It requires a PR and the GitHub Actions status `check`. There are no listed bypass actors. The minimum approval count is zero, but the rule enables extra approval for unattributed changes. Strict status checks are off: GitHub does not require the PR branch to be up to date with `main`. `ci.yml` runs on `pull_request` (default activities: opened, synchronized, reopened) and pushes to branches other than `main` (`branches-ignore: [main]`). It has no path filter, so a pipeline-only or docs-only PR still runs it. The `main` push does not rerun it against the merged SHA. (`.github/workflows/ci.yml:3–31`.)
- **CI inputs and commands.** The job uses Node 22, `npm ci`, and Python 3.12. It runs `python3 pipeline/split_data.py` on committed `site/data.json` and `python3 pipeline/prerender.py` on the committed snapshots plus registry, archive-cache, and template inputs. It does **not** pass `--write-static-baselines`. It then runs `npm run check`. (`.github/workflows/ci.yml:12–31`, `pipeline/split_data.py:245–259`, `pipeline/prerender.py:1395–1408,1426–1450,1471–1475`, `package.json:5–10`.)
- **`npm run check`.** `run-check.mjs` runs `check-pages-sync.mjs` (five fake R2/Builder cases for interruption, resume, no-op, cleanup, and legacy objects), `check-site.mjs` (static markup, metadata, headers, discovery, file references, budgets, and fixture page manifest/object checks), and `check-worker.mjs` against `local-worker.mjs`. The local Worker uses committed JSON and sampled prerendered routes. HTTP checks cover document routing and HTML/Markdown negotiation, discovery, redirects and 404/410, data methods/revalidation/`Last-Modified`, R2 error and fallback behavior, and the search API contract with stubs. The build endpoint check expects a 403 for an unauthenticated GET. (`scripts/run-check.mjs:75–97,118–124`, `scripts/check-pages-sync.mjs:88–155`, `scripts/check-site.mjs:69–132,172–257,278–418`, `scripts/local-worker.mjs:64–111,125–151,217–225`, `scripts/lib/worker-fixtures.mjs:37–81`, `scripts/check-worker.mjs:89–179,240–301,325–418`.)
- **Not in CI.** No `build_data.py` feed collection or enrichment, `search_docs.py`, real Builder image or cron run, production bindings, or browser/axe check. The local harness disables Builder and stubs AI Search. `check:browser:local` is a separate command. A green check on split and page fixtures is not a check of the next generation. (`.github/workflows/ci.yml:27–31`, `scripts/lib/local-entry.mjs:1–25,48–50`, `scripts/local-worker.mjs:125–151`, `scripts/run-check-browser.mjs:1–6`.)
- **Deploy / Post-deploy.** Deploy runs `npm ci` and `npx wrangler deploy`, not `npm run check`. Install and packaging errors can fail Deploy. After a successful Deploy, Post-deploy uses the default-branch checkout, not the deployed SHA's test scripts. It runs live HTTP smoke (12 probes including revalidation) and Chromium verification (UI, accessibility, split parity, navigation, and a sampled live news record). It can also run on demand. It tests what the public site serves at that moment, not necessarily the next Builder generation. A failed verification reports a failure but does not roll back. (`.github/workflows/deploy.yml:19–38`, `.github/workflows/post-deploy.yml:3–38`, `scripts/live-smoke.mjs:7–16,22–94`, `scripts/verify-browser.mjs:6–18,239–310,338–425`.)
- **Freshness / Ora.** Build freshness runs on a GitHub schedule set to `:43` UTC or on demand. It sends `HEAD /data-hot.json` and fails on HTTP errors, missing or invalid `Last-Modified`, or age over 75 minutes. The header is the R2 upload time. If the split is missing, the Worker can serve the full snapshot at that URL. A fresh timestamp does not establish correct data, fresh pages, an updated search index, or even a complete split. A single missed tick need not cross the threshold. Weekly Ora runs Monday at 08:23 UTC or on demand. It reports live scores and failed check IDs, but does not fail the job for low scores or failed scan checks. Neither workflow gates publication. (`.github/workflows/build-freshness.yml:6–9,19–50`, `worker/data.js:22–63`, `.github/workflows/ora-weekly.yml:3–6,16–47`.)

## What the Builder publishes

At `:07` UTC the deployed Worker calls the deployed Builder. `/__build` calls the same build function. On each run the container fetches the **whole repository archive** at `https://codeload.github.com/askgina/cyber/tar.gz/refs/heads/main`. This is the tip at fetch time, not a SHA supplied by Deploy or identified by a passing check. The Dockerfile copies only `server.py` into the image. The container extracts the tarball and overlays the previous R2 `state.tar.gz` for the `STATE` allowlist: caches and working state, including `pipeline/archive_cache`, private prerender state, and the two snapshots. The three curated JSON files in the table are not overlaid. The container then runs `build_data.py`, `search_docs.py`, and `prerender.py`, in that order. Production generation also depends on external feeds and stored state, not just Git. (`wrangler.jsonc:32–35,55–64`, `worker/index.js:29–46,224–235`, `container/Dockerfile:1–5`, `container/server.py:14–24,27–51,54–95`, `pipeline/build_data.py:14–17,510–516`.)

Publication is **not one transaction**. The Worker writes full data, archive, and state as separate objects. It reads all three split parts before writing them, writes hot last, and falls back to the full data if split sync fails. It uploads changed search documents and requests indexing. It writes the page manifest after the referenced uploads succeed. That controls when new manifest entries are visible, not an atomic switch for all objects or outputs. A nonzero `build_data.py` exit stops the build before these writes. Nonzero exits from `search_docs.py` and `prerender.py` are reported but do not by themselves block the data publish. Search and page sync errors can be logged while the Worker still reports `build ok`. (`container/server.py:73–95`, `worker/index.js:19–25,38–85,112–140`, `worker/pages.js:73–86,105–151`.)

## Ungated routes and failure modes

Here, **ungated** means there is no automated check that must approve the actual production candidate before it is served. It does not mean `main` accepts unreviewed direct pushes or that no checks exist.

- **Hourly and manual Builder output.** Full ingestion, curated changes, search indexing, and actual generated pages can publish without a test of the generation. The `incidents.json` fixture prerender check is useful but partial. `/__build` applies the same publication rules as cron.
- **Deploy and configuration integration.** PR CI covers local behavior, not the real Builder image, Cloudflare bindings, or browser behavior. Deploy publishes before live verification. There is no same-SHA recheck between merge and deployment. A manual or authorized operator deploy has no independent status prerequisite in the deploy code.
- **Verification and workflow changes.** Scripts and workflow files can change what gets checked without triggering a deploy or exercising those checks. No verifier runs automatically for each Builder generation. A successful smoke run immediately after a mixed Worker/pipeline deploy does not establish that the new pipeline ran.
- **Partial publication.** Fresh JSON can mask stale pages, a stale archive, a missing split, or stale search results. A later `Last-Modified` is evidence of a write, not data quality, generation completeness, or the source SHA.

## Options for #37

| Option | What must pass before publication | Code sites and tradeoffs |
| --- | --- | --- |
| **Keep building `main`; improve the required PR check** | Keep `check` as the merge gate. Add curated input parse/schema checks and a deterministic pipeline test on recorded feeds and state. Include `search_docs.py` and the browser gate if they are expected to block merges. | Extend `.github/workflows/ci.yml:11–31` and `scripts/run-check.mjs:118–124` (or a separate required job and ruleset entry). No ref change at `container/server.py:14,27–42`. Lowest latency and operational cost. Still does not validate the exact merged SHA or the artifacts made from live feeds. |
| **Build only a checked ref** | On every `main` push, including pipeline-only pushes, check the exact merged SHA. Move a dedicated Builder ref only after the chosen checks pass. Keep the last good ref on failure. If both push types share a workflow, promote only from a successful `main` run. | Add a promotion workflow or extend `.github/workflows/ci.yml:3–31`. Restrict ref updates to the promotion actor, and prevent older runs from moving the ref backward. Resolve the promoted ref to a SHA and fetch that SHA in `container/server.py:14,27–42`. Report the selected SHA and generation through `container/server.py:94–95` and `worker/index.js:56–65`. This isolates failed source revisions and supports reverting the build source. It adds promotion lag and a ref that can stall. It still does not check artifacts from later live inputs or roll back the deployed Worker/image. Coordinate incompatible changes across the two publishers. |
| **Check each generated candidate inside the Builder** | Use one downloaded SHA and restored state to generate a candidate. Require input parse/schema checks, split parity and budgets, archive generation, page manifest/object integrity, and search document checks as appropriate. Reject the candidate before the Worker writes production objects if any required output fails. | Add validation between generation and `pack_outputs` in `container/server.py:73–95`. Reuse selected check logic from `pipeline/split_data.py`, `scripts/check-site.mjs`, and `scripts/check-pages-sync.mjs`. A Node/browser gate would also require image dependencies (`container/Dockerfile:1–5`) and more time. `worker/index.js:48–63` and `worker/pages.js:73–141` would need generation-scoped staging and a publication pointer if the decision requires an all-or-nothing cutover. This verifies the actual generated files for both triggers, but costs runtime in the approximately 15-minute build window. Upstream problems can hold back otherwise usable output. Search indexing is asynchronous and needs a separate readiness policy. |

A checked ref answers **which code may run**. A candidate check answers **which generated output may go live**. They can be combined. Decide whether a split, archive, page, or search failure should stop the entire generation or only its own output. Record the build SHA and per-output generation in either case so monitoring can distinguish an old-but-healthy output from a failed publication. A production smoke test after the write remains detection, not prevention.

## Live evidence and limits

Source reviewed at [`625e462`](https://github.com/askgina/cyber/commit/625e462bdc2ce5d632735e7f1c4c791cffebcb2f). Line references point to that revision. GitHub evidence came from read-only `gh run list -R askgina/cyber`, `gh run view`, and `gh api repos/askgina/cyber/rulesets/28174271`.

- PR #31 shows [CI on branch push](https://github.com/askgina/cyber/actions/runs/45827366494), [CI on pull request](https://github.com/askgina/cyber/actions/runs/45827374850), [Deploy on the merge push](https://github.com/askgina/cyber/actions/runs/45827528869), and [successful Post-deploy](https://github.com/askgina/cyber/actions/runs/45827636575). The PR job logged five page sync cases, 33,036 static checks, and 589 local Worker checks. Those are run results, not fixed totals.
- `625e462` changed only `pipeline/prerender.py`. `gh run list -R askgina/cyber --commit 625e462bdc2ce5d632735e7f1c4c791cffebcb2f` returned no runs at the time of review. This example predates the ruleset's creation. Under the current ruleset a corresponding PR needs `check`, but the merge push still does not trigger a workflow. An empty run list does not show whether Cloudflare built the commit.
- A [scheduled freshness failure](https://github.com/askgina/cyber/actions/runs/45810812152) reported a 249-minute-old output against the 75-minute limit. Its actual start was 11:27 UTC, so `:43` is a schedule, not an execution guarantee. A later read-only HEAD during review returned `200` and `Last-Modified: Thu, 26 Nov 2026 15:15:15 GMT`. That is an upload timestamp, not proof of a deployed SHA.
- No production build, deploy, or change to configuration or the ruleset was performed for this inventory. The timing and gate claims describe repository wiring and observed runs, not a Cloudflare SLA or an account-wide audit of external operators.
